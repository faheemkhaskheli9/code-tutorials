Every RAG tutorial I open starts with pip install langchain chromadb openai and ends with a chatbot I can't debug. Four hundred megabytes of dependencies, three abstraction layers, and when the answers come back wrong I have no idea which layer lied to me.

So here's the opposite. One file, about 100 lines, four dependencies you probably already have, and no API key. It chunks a folder of Markdown, embeds it with a small local model, retrieves by cosine similarity, and has a language model answer only from what it retrieved - or say "I don't know" when retrieval comes up empty. Every piece is small enough to read in one sitting, which means when it misbehaves you can actually find out why.

It runs on a laptop CPU. The first run downloads about 400 MB of model weights and takes roughly four minutes; after that the whole script finishes in 15 seconds.

The corpus is fake, and that's the point

The docs/ folder holds four pages of documentation for a deployment CLI called Quokka. Quokka doesn't exist. I made it up - the port numbers, the error codes, the rollback semantics, all of it.

That's deliberate. If I point a RAG demo at the Python docs, a language model can answer most questions from memory and I learn nothing about whether my retrieval works. With an invented tool, a correct answer has to have come through the pipeline. When the model tells me the dev server runs on port 7717, that number could only have arrived one way.

If you're building RAG over real internal docs, steal this trick for your test set. Invent a page. If the system answers questions about it, retrieval is doing its job.

Chunking: the boring part that decides everything

Embedding a whole document into one vector is useless - you get the average meaning of 2,000 words, which is nobody's question. So documents get split. This is where most RAG quality is won or lost, and it's the part people skip past to get to the model.

def chunk(text, size=CHUNK_CHARS, overlap=OVERLAP_CHARS):
    """Split into overlapping pieces, cutting at whitespace, always moving forward."""
    pieces, start = [], 0
    while start < len(text):
        end = min(start + size, len(text))
        if end < len(text):
            snap = text.rfind(" ", start, end)
            if snap > start:
                end = snap
        if text[start:end].strip():
            pieces.append(text[start:end].strip())
        if end >= len(text):
            break
        start = max(end - overlap, start + 1)
    return pieces

Three decisions in there worth defending.

600 characters with 100 of overlap. Small enough that a chunk is about one idea, big enough to carry the sentence that gives it context. The overlap exists so a fact that straddles a boundary survives in at least one chunk intact.

Snap to whitespace. Cutting at a fixed offset splits words in half, which corrupts the tokens you're about to embed for no benefit at all. rfind(" ", start, end) walks back to the last space in the window. Two lines, better vectors.

That max(end - overlap, start + 1) guards a real bug. If overlap ever approaches chunk size, or the whitespace snap pulls end back near start, then start = end - overlap can move backwards and the loop spins forever emitting the same chunk. I'd rather have one max() than a hang in production. This is the kind of thing a framework hides from you until the day it doesn't.

Embeddings without sentence-transformers

sentence-transformers is a fine library, but it's another dependency wrapping something that's twelve lines of transformers. MiniLM gives you one vector per token; you need one per chunk. The standard move is a mean over the tokens, and the only subtlety is ignoring the padding.

class Embedder:
    """MiniLM + mean pooling + L2 normalisation, so cosine similarity is a dot product."""

    def __init__(self, name=EMBED_MODEL):
        self.tok = AutoTokenizer.from_pretrained(name)
        self.model = AutoModel.from_pretrained(name).eval()

    def __call__(self, texts):
        batch = self.tok(texts, padding=True, truncation=True, max_length=256, return_tensors="pt")
        with torch.no_grad():
            hidden = self.model(**batch).last_hidden_state
        mask = batch["attention_mask"].unsqueeze(-1).float()
        pooled = (hidden * mask).sum(1) / mask.sum(1).clamp(min=1e-9)
        return torch.nn.functional.normalize(pooled, dim=1).numpy()

The attention_mask multiply is the line that matters. Without it you average real tokens together with padding tokens, and short chunks get dragged toward whatever [PAD] happens to embed as. Longer chunks then look artificially different from short ones, and your ranking quietly degrades in a way that's very hard to notice.

Normalising to unit length is a convenience with teeth: once every vector has length 1, cosine similarity is the dot product, so the search step becomes a matrix multiply instead of a loop with divisions in it.

The vector database is a NumPy array

Fifteen chunks. Three hundred and eighty-four dimensions. That's a 15×384 float array - about 23 kilobytes. Installing Chroma or Pinecone to hold 23 kilobytes is not engineering, it's shopping.

def build_index(embed, docs=DOCS):
    if not docs.is_dir():
        raise SystemExit(f"No docs directory at {docs}")
    chunks, sources = [], []
    for path in sorted(docs.glob("*.md")):
        for i, piece in enumerate(chunk(path.read_text(encoding="utf-8"))):
            chunks.append(piece)
            sources.append((path.name, i))
    return {"vectors": embed(chunks), "chunks": chunks, "sources": sources}


def search(question, index, embed, top_k=TOP_K):
    scores = index["vectors"] @ embed([question])[0]
    order = np.argsort(-scores)[:top_k]
    return [(float(scores[i]), index["chunks"][i], index["sources"][i]) for i in order]

Search is two lines: one matrix multiply, one sort. A real vector database earns its place when you have millions of vectors and need approximate nearest neighbours, or when several processes share an index. At 15 chunks, or 15,000, exact brute-force search is faster than the network hop to the service that would do it approximately.

Note that sources carries the filename and chunk position alongside every vector. Retrieval without provenance is just a language model with extra steps - if you can't show the user where an answer came from, you can't let them check it.

Grounding: the part people get wrong

Here's the bit that separates RAG from a party trick. A language model handed retrieved text will happily answer even when the retrieval was garbage. The fix is two guards, not one.

PROMPT = (
    "Answer the question using only the context below. If the context does not "
    "contain the answer, reply exactly: I don't know.\n\n"
    "Context:\n{context}\n\nQuestion: {question}\nAnswer:"
)


def answer(question, index, embed, generate):
    hits = search(question, index, embed)
    if not hits or hits[0][0] < MIN_SCORE:
        return "I don't know - nothing in the docs is close enough.", []
    context = "\n\n".join(text for _, text, _ in hits)
    return generate(PROMPT.format(context=context, question=question)), hits

The prompt instruction is the soft guard. MIN_SCORE is the hard one: if the best chunk scores below 0.25, the model never gets called at all. No context, no prompt, no opportunity to improvise. That threshold is the cheapest hallucination defence in the whole pipeline and it costs one if.

The generator is passed in as a function, which is the one bit of indirection I'll defend. It buys the swap to a hosted model for free:

def hosted_generate(prompt):
    """Where a hosted model plugs in - same prompt, better answers. `pip install anthropic`."""
    import anthropic  # deliberately not in requirements.txt: the local path needs no key

    msg = anthropic.Anthropic().messages.create(
        model="claude-opus-5", max_tokens=1024,
        messages=[{"role": "user", "content": prompt}],
    )
    return next(b.text for b in msg.content if b.type == "text").strip()

Same retrieval, same prompt, different last mile - python main.py --hosted "...". That path needs an API key, so it is not what produced the output below; everything you're about to see ran locally on CPU.

Gotchas

The third question is a generator failure, not a retrieval failure. Look at the score: 0.614 on troubleshooting.md #0, the single highest score in the whole run, and that chunk opens with the exact answer ("Another deploy holds the lock... wait for it to finish"). Retrieval was perfect. Flan-T5-small, at 77 million parameters, read it and said "i don't know" anyway. Small models take the escape hatch you give them, especially on open-ended phrasings like "what should I do?" - that's what --hosted is for, and it's exactly why I keep the score next to every answer. Without the scores I'd have spent an hour tuning chunk size to fix a problem that was never in the retriever.

The correct answer scored 0.294 against a 0.25 cutoff. The port question worked, but by 0.044. Absolute cosine scores from MiniLM are not intuitive: correct matches routinely land in the 0.3s, not the 0.8s you might expect. Tune MIN_SCORE against questions you know the answers to, and check what your off-topic questions score before you raise it. I picked 0.25 by running the France question and seeing where it landed.

The Markdown leaked. The answer came back as **port 7717** because the source document had it in bold. The model is extracting verbatim, asterisks and all. Charming in a terminal, not something you want in a web UI - strip Markdown at ingestion or at display, but decide which.

Numbering the context chunks made things worse. My first version labelled each retrieved chunk [1], [2], [3] so the model could cite them. Flan-T5-small's answer to the E_LOCKED question was, in full: [3]. It learned to output a citation marker instead of an answer. Small instruction-tuned models copy the most distinctive pattern in the prompt. Citations now come from the retrieval metadata, printed by the code - which is more trustworthy anyway, since a model can't fake a citation it was never asked to produce.

Where to go next

Persist the index. Right now every run re-embeds all 15 chunks. Save the array with np.save and give each chunk an id that's a hash of (filename, position, chunk text) - hashing the text too, not just the position, means an edited chunk gets a new id instead of silently overwriting the old one under a stale key. That one choice is what makes re-ingestion safe to run on a cron.

Add keyword search alongside the vectors. Embeddings are bad at exact strings - E_LOCKED and E_NO_PROD_FROM_DEV look nearly identical to MiniLM. A BM25 score merged with the cosine score fixes error codes, version numbers and function names, and it's about 30 more lines.

Build a tiny eval set. Twenty questions with the filename you expect back, then measure how often the right chunk is in the top 3. It turns "the chunking feels better now" into a number, and it's the only way to know whether a change helped.
